## Time and status rules

Earlier conversation messages supplied a date but no exact message timestamps. Their entries below are **retrospective**, with decision date **15 October 2026, exact time unavailable**. The recording timestamp above is when this reconstruction was recorded, not a fabricated time for those earlier decisions. The actual interview date is also unknown.

For every future decision, capture the current time in Europe/London as ISO 8601 with its UTC offset, record the decision-maker and source, and commit the change normally. Git author/committer dates identify when a record entered history; they do not prove when a prior conversation occurred. Do not backdate commits.

Statuses: **Confirmed** means Samuel chose the direction; **Constraint** comes from the assessment brief; **Proposed** is an agent recommendation; **Open** still needs a choice; **Superseded** preserves an earlier choice/proposal replaced by a later entry. Confirmation of an evaluation scenario is not approval of a vendor purchase or a production launch.

When a choice changes, append a new numbered entry referencing the earlier ID. Update the current-status index and plan, while retaining the old event and rationale. Keep decision IDs in related commit messages. Record implementation results separately from intentions; passing a demo test does not retroactively prove a proposal was correct.

### D023 Server-rendered FastAPI + SQLite instead of a React frontend

- **Decision time:** 2026-10-15T18:19+01:00 (approx., at build start). **Owner/status:** Devin proposal under D022's "simpler familiar equivalent" allowance; not a Samuel technical selection.
- **Source:** Handoff prompt; observed environment (no Node.js installed on the Devin VM; Python 3.10 available).
- **Choice:** FastAPI + stdlib `sqlite3` + Jinja2 server-rendered pages. A few lines of inline JavaScript post to the same JSON API that the direct API checks use, so UI and API share one enforcement path. No ORM, no frontend build.
- **Why:** One dependency ecosystem, one run command, no build step, simpler review for a maintainer and a trivial container image. Spends the 120 minutes on shared controls rather than toolchain setup.
- **Alternatives:** React/TypeScript SPA (D022 default) adds Node, a second package manager, session/CORS wiring and a build step without demonstrating additional control value at this size. SQLAlchemy is unnecessary for six tables.
- **Effect:** Plainer client UX; customization happens in templates/Python. A production portal with many tools might adopt a component framework.
- **Validation:** `pytest` 7/7 passing; pages visually checked in a browser (see build notes).

### D024 Shared mutation helper, optimistic versions and session-derived identity

- **Owner/status:** Devin implementation choice under D007/D022; implemented.
- **Choice:** Every mutation calls `run_command` in `app/core/commands.py`: permission check → reason validation (3–500 chars) → `BEGIN IMMEDIATE` transaction → expected-version check → module transition function → guarded `UPDATE … WHERE version = ?` → audit insert (actor username and role from the session) → commit. Request models ignore unknown fields, so client-supplied `actor`/`role` values have no effect. Audit reads are scoped per role (`AUDIT_SCOPE`); only the auditor sees all modules.
- **Why:** Makes "state and audit commit together", stale-write rejection and server-side authority a single reviewed code path new modules reuse.
- **Alternatives:** Per-module checks (drift risk); row locks or queues (unnecessary for a SQLite demo).
- **Effect:** A local SQLite audit table is not tamper-evident retention; SQLite single-writer locking is not a production concurrency design.
- **Validation:** Denied, forged, stale, invalid-transition and concurrent-write checks pass (build notes). An early version stored the numeric user id as the audit actor; corrected to username during review.
