## Minimum working scope

| Surface | Build this slice | Evidence it provides |
| --- | --- | --- |
| Home | Three app links/cards, a short purpose/owner label and current identity. | A common distribution point and an obvious pattern for future tools. |
| Counterparty review, mapped to KYC | List fictional insurers/providers, inspect a synthetic rating/evidence summary, record an approve/reject review with a reason. | Contextual review, authority, state validation and traceable decisions. |
| Claims/payment requests, mapped to refunds | List requests with amount/currency/status and linked counterparty; record a simulated approval with a reason. | Shared entity context and controlled financial-workflow actions. Approval does not move money or establish settlement. |
| Feature flags | List a few sandbox configuration values; change one boolean with a reason. | A third module reusing permission, version and audit helpers. |
| Audit | One history view, filterable at least by module/resource. | Accepted actions from all three modules use the same event model. |
| Identity | Seeded demo accounts with a standard server-managed session and permissions checked at every endpoint. | Direct API denials and role-aware access across the portal. This is demo authentication, not enterprise SSO. |

Use fictional entities and clearly marked synthetic rating/payout evidence. Record rating source/type, rated entity or market, as-of date and provenance separately. Financial-strength opinions and observed payout history are different evidence. The counterparty review is an insurance proxy, not a complete KYC identity or compliance engine.

## Small permission model

Use seeded accounts and a small action-permission map. Keep repository contribution/review authority separate from business-operation permissions. An engineer does not automatically gain claims-approval authority.

| Demo role | Read module records | Record counterparty review | Approve demo claim | Change sandbox flag | Read permitted audit history |
| --- | --- | --- | --- | --- | --- |
| Reviewer | Yes | Yes | No | No | Own/allowed case history |
| Claims operator | Yes | No | Yes | No | Own/allowed request history |
| Flag operator | Yes | No | No | Yes | Own/allowed flag history |
| Auditor | Yes, synthetic summaries | No | No | No | Yes across modules |

Hiding a button is a UX convenience; the server must also reject forbidden calls. Derive actor and permissions from the server session. Scope audit fields appropriately; this demo contains no real personal documents.

## Shared implementation

Use one repository, one backend and one database. The proposed default for an empty repo is React/TypeScript, FastAPI and SQLite; a simpler familiar equivalent is acceptable if recorded. Prefer ordinary, reviewable dependencies and a short run command over infrastructure setup.

Keep shared session/permission checks, database transactions, version checks, audit writing and errors in a small common layer. Counterparty, claim and flag commands call it through explicit module operations. Accepted state and its corresponding audit event commit together. Persist data across restart; a deliberate seed/reset command must not overwrite accepted work on every launch.

The integration story is concrete and small: a counterparty record links to its claim requests, the same identity boundary governs all tools, and an auditor follows actions across modules. Flags can remain global to the sandbox. Do not invent a rule that a rating or KYC approval automatically authorizes a payment.

Use a shared server API and a relational data store for the demo. Provider adapters may return fixtures. Keep their boundary clear, but do not describe a fixture as a completed real connector integration. MCP is a future option only if there is a defined AI-to-application interaction.

## Verification that earns demo claims

Check these behaviors rather than accumulating superficial tests:

1. Each module has its promised working slice and displays accepted state/history.
2. An auditor cannot submit any mutation by directly calling the API. Another role is denied an action outside its permission set.
3. A forged client role/actor field does not grant authority or change attribution.
4. Missing reason, invalid transition and stale version are rejected without an accepted state change.
5. Two writes using one starting version yield at most one accepted change and its corresponding audit event.
6. Restart preserves state and history. Seed/reset is explicit.
7. Counterparty/claim links identify the same underlying entity; all three modules call the same shared permission/history implementation.
8. A new maintainer can follow the run instructions; record actual issues found.

Samuel should independently choose a forbidden/stale case and trace one privileged request. The prototype establishes only the observed synthetic behaviors, not production SSO, immutable retention, real payment execution, sustained reliability or annual savings.
